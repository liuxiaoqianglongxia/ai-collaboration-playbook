# 榨干 GPT 订阅：把 ChatGPT、Codex、Claude Code 和 GitHub 组成一条工程流水线

版本：V0.2.6 Full Whitepaper Recovery  
状态：技术分享文章归档稿  
定位：面向普通用户和小团队，解释如何把 GPT 订阅从“聊天工具”用成“项目协作系统”

---

## 1. 先说结论

很多人买了 GPT 订阅，只把它当成一个聊天窗口，或者只盯着 Codex 额度。这样用当然也有价值，但远远没有把订阅榨干。

更有效的用法是把工具分工：

```text
ChatGPT：总控、架构判断、任务拆解、验收
GitHub：唯一事实源、状态机、留痕系统
Codex：交付收口、改代码、跑测试、提交 PR
Claude Code：工程探索、调用链分析、局部复审
便宜模型：放进强工具壳里做批量苦力、草稿、初筛、资料整理
```

这不是为了炫技，而是为了让一个普通人也能像小型工程团队一样工作。

---

## 2. 为什么只聊天不够

普通聊天的问题在于：

```text
上下文越来越长
历史结论容易丢
项目状态散落在多轮对话里
执行结果没有落地
下一个会话不知道上一个会话做了什么
```

如果所有事情都停留在聊天里，就会出现三个后果。

第一，AI 会越来越像在猜。它可能记得一个方向，但不知道当前仓库到底是什么状态。

第二，执行者会重复劳动。Codex、Claude Code 或其他工具每次都要重新理解上下文。

第三，验收很虚。你看到它说“已完成”，但没有 GitHub 文件、commit、diff、报告，就无法判断到底完成了什么。

所以要把 GPT 订阅用成工程系统，第一步不是找更强的提示词，而是建立事实源。

---

## 3. GitHub 为什么是核心

GitHub 在这套方法里不是代码托管工具那么简单，而是项目事实源。

它负责保存：

```text
当前项目状态
任务列表
关键决策
执行报告
验收记录
代码 diff
PR 讨论
回滚路径
```

建议每个项目至少有：

```text
CHATGPT_START_HERE.md
CURRENT.md
TASKS.md
DECISIONS.md
AGENTS.md
CLAUDE.md
reports/latest.md
reports/codex/latest.md
reports/claude/latest.md
```

有了这些文件，新会话不需要问“我们上次聊到哪了”，它可以直接读仓库。

一句话：

```text
聊天负责讨论，GitHub 负责事实。
```

---

## 4. ChatGPT 应该怎么用

ChatGPT 最适合做总控。

它不一定要亲自跑命令，也不一定要直接改文件。它更适合做：

```text
理解真实目标
判断项目是不是值得做
判断现在应该先做什么
把任务拆成可执行包
定义禁止事项
定义验收标准
审 Codex 报告
决定下一步
```

ChatGPT 的强项是全局判断和语言组织。你可以把它当成项目经理、架构师和验收官的混合体。

一个典型指令是：

```text
请先读取 GitHub 事实源，不要凭聊天记忆判断当前状态。
然后根据 CURRENT.md、TASKS.md、reports/latest.md，给我下一轮 Codex 任务包。
```

重点是：不要让 ChatGPT 只在聊天里写一大段“你去做什么”。正式执行要落到 GitHub 任务文件。

---

## 5. Codex 应该怎么用

Codex 适合做交付收口。

它应该拿到明确任务文件，然后：

```text
读任务
读仓库
改允许范围内的文件
跑测试
检查 diff
写报告
提交 PR
```

Codex 不是万能自由职业者，它需要边界。

一个好的 Codex 任务包应该包含：

```text
目标
背景
允许修改范围
只读范围
禁止范围
执行步骤
验收标准
报告要求
停止条件
```

这样 Codex 不会因为“看起来顺手”就改到别的模块，也不会因为上下文不清楚而误碰生产配置。

---

## 6. Claude Code 应该怎么用

Claude Code 适合做工程探索。

它特别适合：

```text
长文件阅读
调用链分析
测试失败定位
错误栈解释
diff review
局部修复草案
```

但它不应该替代 Codex 做最终交付。更安全的方式是：Codex 生成一个 Claude Code task-file，让 Claude Code 只做分析或局部草案，输出报告，然后 Codex 复核和收口。

推荐模式：

```text
Codex 负责最终提交。
Claude Code 负责工程探索。
ChatGPT 负责最终验收。
GitHub 负责留痕。
```

这样可以节约 Codex 的探索额度，也能发挥 Claude Code 的工程阅读能力。

---

## 7. 便宜模型怎么放进强工具壳

很多工作不需要最贵模型一直做。

便宜模型适合：

```text
资料初筛
批量摘要
草稿整理
日志归类
重复格式转换
测试报告初步归纳
角色或模板初稿
```

但便宜模型必须放在强边界里使用。

它可以做“素材生产”，不能直接做“最终裁决”。

推荐分工：

```text
便宜模型：生产候选内容
Codex：检查文件、集成、测试
ChatGPT：判断是否采用
GitHub：记录最终事实
```

这就是“便宜模型放进强工具壳”的核心：不是让便宜模型单独负责结果，而是让它在任务文件、事实源、验收标准、执行报告的框架内做苦力。

## 8. 一条完整工作流

一个项目可以这样跑：

```text
1. ChatGPT 读取 GitHub 事实源
2. ChatGPT 生成 Codex 任务文件
3. Codex 按任务文件执行
4. Codex 发现需要工程探索
5. Codex 生成 Claude Code task-file
6. Claude Code 输出只读分析报告
7. Codex 复核报告并完成修改
8. Codex 跑测试并提交 PR
9. ChatGPT 读取 PR / diff / reports
10. ChatGPT 给出 PASS / PARTIAL PASS / FAIL / BLOCKED
11. 结论写回 GitHub
```

这条流程听起来比聊天麻烦，但它解决了长期协作最难的问题：状态稳定、责任清晰、证据可查。

## 9. 小白怎么开始

第一步，不要先开发功能，先给项目建协作底座。

最小文件：

```text
CHATGPT_START_HERE.md
CURRENT.md
TASKS.md
DECISIONS.md
AGENTS.md
reports/latest.md
```

第二步，让 ChatGPT 只做判断，不急着让 Codex 写代码。

第三步，把每个执行任务变成任务文件。

第四步，让 Codex 按任务文件执行并写报告。

第五步，让 ChatGPT 按 GitHub 事实源验收。

只要做到这五步，项目就已经从“聊天驱动”变成了“事实源驱动”。

## 10. 一个可复制的任务包提示词

```text
请读取当前项目的 GitHub 事实源：
CHATGPT_START_HERE.md、CURRENT.md、TASKS.md、DECISIONS.md、reports/latest.md。

不要凭聊天记忆判断项目状态。

请生成一份 Codex 任务包，包含：
1. 背景
2. 目标
3. 允许修改范围
4. 禁止事项
5. 执行步骤
6. 验收标准
7. 报告要求
8. 停止条件

本轮不要部署，不改数据库，不改 .env，不跨项目写入。
```

## 11. 最常见的坑

```text
坑 1：只聊天，不落 GitHub。
坑 2：没有任务文件就让 Codex 开干。
坑 3：Claude Code 输出未经复核就采纳。
坑 4：把便宜模型输出当最终结论。
坑 5：没有 reports/latest.md，下一轮完全接不上。
坑 6：生产环境和开发环境混用。
坑 7：Windows / WSL 路径和 shell 命令写错。
```

解决方法就是一句话：

```text
事实源先行，任务文件驱动，报告闭环，验收看证据。
```

---

## 12. 这套方法适合谁

适合：

```text
一个人做多个项目
小团队用 AI 协作
有 GitHub 仓库
需要长期维护状态
不想每次开新会话都从头解释
希望把订阅额度用在刀刃上
```

不适合：

```text
只想临时问答
完全不愿意维护仓库
没有长期项目
不需要复盘和验收
```

---

## 13. 最后的判断

GPT 订阅真正的价值，不只是“模型回答得更好”，而是让你把多个工具组合成一个工作系统。

```text
ChatGPT 负责想清楚。
GitHub 负责记清楚。
Claude Code 负责看清楚。
Codex 负责做清楚。
便宜模型负责干苦力。
```

当它们围绕同一个事实源工作时，一个人就能拥有接近小型工程团队的协作能力。

这才是榨干 GPT 订阅的关键。
